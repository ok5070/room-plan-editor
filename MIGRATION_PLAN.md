# План миграции к схеме 0.1

Статус: план безопасного перехода; миграция ещё не реализована.

Цель — преобразовать существующие ProjectRecord в контракт `DATA_CONTRACT.md`
без потери исходников, ручной геометрии, оборудования и связей.

## 1. Принципы

1. Миграция никогда не выполняется без резервной копии исходной записи.
2. Исходные файлы не изменяются и не переименовываются в первой миграции.
3. Преобразование детерминировано и идемпотентно.
4. Ошибка любого шага оставляет исходный проект доступным.
5. Новая запись активируется только после полной проверки.
6. Неизвестное происхождение маркируется `legacy`, а не угадывается.
7. Нельзя выдавать автоматически мигрированные элементы за подтверждённые.
8. Миграция данных отделена от повторного распознавания CAD.
9. Откат не требует обратного преобразования новой схемы в старую.

## 2. Поддерживаемый исходный формат

Legacy-проект определяется отсутствием верхнеуровневого `schema_version` и
наличием комбинации:

```text
id
name
files[]
project
geometry
updatedAt
```

Необязательные CAD-поля могут отсутствовать. Мигратор не должен считать
`cadSelectedLayout`, `cadAppliedLayout`, master-поля или `cadAreas` обязательными.

Проект с неизвестным непустым `schema_version` автоматически не мигрируется.

## 3. Стратегия хранения

Рекомендуемая переходная структура:

```text
data/projects/<project_id>/
├── project.json                    # активная запись
├── project.legacy.json             # резервная копия до 0.1
├── migration-0.1-report.json       # результат и проверки
├── sources/                        # вводится позднее или адаптером
├── revisions/
└── releases/
```

На первом этапе исходные файлы могут оставаться рядом с `project.json`, если
SourceFile использует существующий `storage_ref`. Физическое перемещение файлов
в `sources/` выполняется отдельной миграцией и не совмещается со сменой модели.

## 4. Этапы миграции одного проекта

### 4.1. Предварительная проверка

Проверить:

- читаемость JSON;
- совпадение ID записи с именем каталога;
- наличие `project` и `geometry`;
- уникальность ID стен, дверей, окон и оборудования;
- существование стен из `wallId`;
- корректность `hostDoorId`, `hostWallId` и `servedDoorIds`;
- существование файлов из `files[]`;
- отсутствие уже начатой незавершённой миграции.

Неразрешимые ошибки блокируют автоматическую миграцию и попадают в отчёт.
Исправимые нарушения преобразуются в Issue с категорией `migration_warning`.

### 4.2. Резервная копия

1. Вычислить SHA-256 текущего `project.json`.
2. Скопировать его байт-в-байт в `project.legacy.json`.
3. Проверить совпадение размера и хэша.
4. Записать начало операции во временный migration report.

Если резервная копия уже существует с другим хэшем, миграция останавливается и
требует ручного решения.

### 4.3. Project и Metadata

Преобразование:

```text
legacy.id                         → project_id
legacy.name                       → metadata.name
project.project.object            → metadata.name, если legacy.name пусто
project.project.address           → metadata.address
project.project.revision          → metadata.legacy_revision_label
legacy.updatedAt                  → updated_at
```

`created_at` берётся из доступной метаинформации либо устанавливается равным
`updated_at` с пометкой `legacy`.

### 4.4. SourceFile

Для каждого элемента `files[]` создать SourceFile:

- сохранить существующий ID, если он уникален и безопасен;
- иначе создать новый ID и записать соответствие в migration map;
- определить `kind` по расширению;
- определить media type;
- вычислить SHA-256 и фактический размер файла;
- сохранить исходное имя;
- использовать существующий относительный storage_ref;
- установить origin миграции `legacy` в metadata.

Отсутствующий физический файл создаёт блокирующий либо review Issue в зависимости
от политики проекта, но не заменяется пустым файлом.

### 4.5. Sheet

Минимально создаётся один Sheet для текущего активного плана.

Имя выбирается в порядке:

1. `cadAppliedLayout`;
2. `cadSelectedLayout`;
3. `project.floorPlan.name`;
4. `План 1`.

Если `cadAreas` содержит несколько областей, они не становятся автоматически
несколькими подтверждёнными листами: текущий ProjectRecord хранит рабочую
геометрию только одной области. Дополнительные области регистрируются как
доступные source locators и требуют последующего импорта через RecognitionRun.

### 4.6. Architecture

Преобразовать:

```text
geometry.walls[type=wall]          → sheet.architecture.walls
geometry.walls[type=partition]     → sheet.architecture.partitions
geometry.doors                     → sheet.architecture.doors
geometry.windows                   → sheet.architecture.windows
project.floorPlan.rooms            → sheet.architecture.rooms, если валидны
```

Каждый объект получает:

- стабильный ID;
- Placement на созданном Sheet;
- `origin.kind = legacy`;
- `verification.status = unverified` или `review_required`;
- даты из проекта, если собственных дат нет.

Двери с `swing = unknown` остаются неподтверждёнными. Мигратор не угадывает петли
и не преобразует такой объект в подтверждённую дверь.

Импортные `confidence` и `reviewHint`, если присутствуют, сохраняются в Origin и
properties. Их отсутствие не заполняется выдуманными значениями.

### 4.7. Systems и Entity

Каждый элемент `project.equipment[]` переносится в систему по текущему `system`
или таблице legacy-типов.

Объект остаётся листовым, если имеет валидное размещение на активном плане.
Общепроектный объект переносится в `project_systems`, только если это можно
установить без предположения. В сомнительном случае он остаётся на legacy Sheet и
получает migration Issue.

Текущий `status = confirmed` не считается достаточным доказательством инженерного
подтверждения без истории. Он сохраняется как legacy property, а новый
Verification получает `review_required`, если политика проекта не предусматривает
отдельное ручное подтверждение миграции.

### 4.8. Relations

Создать Relation из существующих ссылок:

```text
door.wallId                       → opening_belongs_to_wall
window.wallId                     → opening_belongs_to_wall
equipment.hostDoorId              → equipment_mounted_at_door
equipment.hostWallId              → equipment_mounted_at_wall
controller.servedDoorIds[]        → controller_serves_door
```

Чтобы переходный редактор продолжал работать, встроенные legacy-поля могут
временно сохраняться как вычисляемое совместимое представление. Источником истины
после успешной миграции становятся Relation.

Дублирующие связи объединяются детерминированно. Висячая ссылка не удаляется
молча: создаётся Issue и запись в migration report.

### 4.9. Issues

Автоматически создать Issue для известных состояний:

- дверь без подтверждённых петель;
- отсутствующая несущая стена двери или окна;
- оборудование с отсутствующей host-сущностью;
- контроллер с отсутствующей обслуживаемой дверью;
- превышение ёмкости контроллера;
- отсутствующий source file;
- неоднозначный активный CAD-лист;
- утраченные или неизвестные provenance-поля.

Миграционные issues получают `source = migration-0.1` и не подменяют полную
проверку ruleset.

### 4.10. WorkingModel

Собрать единый WorkingModel:

```text
model_version = 1
sheets
project_systems
relations
issues
updated_at
updated_by = migration-0.1
```

Legacy `geometry` и `project.equipment` не должны оставаться вторым изменяемым
источником истины. На переходный период они формируются адаптером из
WorkingModel либо хранятся только внутри `legacy_payload` без возможности записи.

### 4.11. CAD master-поля

`cadPreview`, `cadPreviewMaster`, `cadGeometryMaster`, `cadEquipmentMaster`,
`cadAreas` и `cadLayouts` не переносятся в WorkingModel как подтверждённые
объекты.

Они сохраняются как:

- кэш представления SourceFile;
- legacy recognition artifact;
- данные для формирования будущего RecognitionRun.

Повторная обработка этих данных не выполняется внутри миграции.

### 4.12. Draft, Revision и Release

Миграция не создаёт Draft: на момент миграции нет достоверного несохранённого
состояния.

Рекомендуется создать `Revision 1` только после того, как инженер откроет
мигрированный проект, просмотрит migration issues и явно выберет «Зафиксировать
ревизию».

Автоматически создавать Release запрещено.

### 4.13. Запись кандидата

Новая модель сначала записывается во временный файл:

```text
project.0.1.candidate.json
```

После записи выполняются структурная и доменная проверки. Только затем файл
атомарно заменяет `project.json`.

## 5. Проверка результата

### 5.1. Структурная

- `schema_version = 0.1`;
- все обязательные коллекции присутствуют;
- ID уникальны;
- все ссылки разрешаются;
- model_version равен 1;
- даты и enum-значения валидны.

### 5.2. Количественная

Сравнить до и после:

- количество исходных файлов;
- количество стен и перегородок;
- количество дверей и окон;
- количество комнат;
- количество оборудования каждого типа;
- количество встроенных legacy-связей и созданных Relation.

Любое необъяснимое уменьшение блокирует активацию.

### 5.3. Геометрическая

Для каждого перенесённого объекта сравнить координаты с допустимой погрешностью.
Миграция не выполняет консолидацию, изменение толщины, распознавание осевых линий
или исправление архитектуры.

### 5.4. Файловая

- каждый SourceFile разрешается в существующий файл;
- размер совпадает;
- checksum повторно вычисляется и совпадает;
- резервная legacy-запись читается и имеет первоначальный хэш.

### 5.5. Визуальная

Для репрезентативных проектов открыть:

- активный лист в 2D;
- оборудование;
- 2.5D;
- список исходников;
- связи двери и оборудования.

Визуальная проверка дополняет, но не заменяет автоматические проверки.

## 6. Идемпотентность

Повторный запуск:

- для проекта `schema_version = 0.1` выполняет только проверку и не создаёт новые
  сущности;
- не дублирует SourceFile, Sheet, Relation или Issue;
- использует детерминированные migration IDs либо сохранённую migration map;
- не изменяет резервную копию;
- не увеличивает model_version.

## 7. Откат

Откат выполняется переключением активной записи:

1. остановить запись проекта;
2. проверить хэш `project.legacy.json`;
3. сохранить ошибочную новую запись как диагностический файл;
4. атомарно восстановить legacy-копию в `project.json`;
5. записать результат отката в migration report;
6. не удалять добавленные служебные файлы до разбора причины.

Откат не удаляет исходники и не использует обратную миграцию.

## 8. Массовая миграция

Перед массовым запуском:

1. создать инвентаризацию всех проектов и версий;
2. запустить dry-run без записи;
3. классифицировать ошибки;
4. выбрать минимум три проекта: простой, многолистовой и с оборудованием;
5. выполнить полную миграцию копий;
6. пройти визуальную и автоматическую проверку;
7. только затем мигрировать остальные проекты по одному;
8. сформировать итоговый отчёт.

Не выполнять миграцию одновременно с работающим редактором проекта.

## 9. Формат migration report

```json
{
  "migration": "legacy-to-0.1",
  "project_id": "project-001",
  "started_at": "...",
  "finished_at": "...",
  "source_hash": "sha256:...",
  "backup_hash": "sha256:...",
  "result_hash": "sha256:...",
  "status": "completed",
  "counts_before": {},
  "counts_after": {},
  "id_map": {},
  "warnings": [],
  "errors": [],
  "checks": []
}
```

Статусы: `dry_run`, `completed`, `failed`, `rolled_back`.

## 10. Последовательность реализации мигратора

1. Реализовать read-only inventory и dry-run.
2. Реализовать резервную копию и проверку хэша.
3. Реализовать чистую функцию `legacy → 0.1` без файловых операций.
4. Покрыть преобразование fixture-проектами.
5. Добавить structural/domain validation.
6. Добавить запись candidate и атомарную активацию.
7. Добавить rollback.
8. Проверить реальные копии существующих проектов.
9. Только после этого разрешить автоматическое открытие с миграцией.

## 11. Критерии готовности

Миграция считается готовой, если:

- dry-run не меняет файлы;
- повторный запуск не меняет результат;
- все существующие исходники сохраняются побайтно;
- количество и координаты объектов не уменьшаются без отчётной причины;
- все legacy-ссылки либо преобразованы, либо представлены Issue;
- ошибка до активации не меняет текущий project.json;
- откат восстанавливает исходный хэш;
- мигрированный проект открывается, сохраняется и повторно открывается;
- новый CAD-импорт после миграции создаёт RecognitionRun/Proposal и не меняет
  WorkingModel.

## 12. Что не входит в миграцию 0.1

- повторное распознавание всех исходников;
- автоматическое исправление геометрии;
- подтверждение дверей и оборудования;
- создание кабелей и трасс из предположений;
- создание Release;
- физическая реорганизация всех исходных файлов;
- удаление legacy backup;
- миграция архива непосредственно в необратимое удаление.

Эти действия выполняются отдельными, проверяемыми процессами после безопасного
перехода структуры данных.
