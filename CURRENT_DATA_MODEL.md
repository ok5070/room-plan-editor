# Текущая модель данных

Статус: описание фактической реализации на 2026-09-17.

Этот документ описывает существующее хранение и обмен данными в
`room-plan-editor` и `elv-auditor`. Он не является целевым контрактом и не
приписывает текущему коду ещё не реализованные гарантии.

## 1. Роли репозиториев

### room-plan-editor

Текущий владелец:

- локальных проектов;
- загруженных исходных файлов;
- выбранной CAD-области;
- редактируемой геометрии;
- оборудования;
- интерфейса 2D и 2.5D;
- части правил связности СКУД.

Основная серверная реализация находится в `main.py`, клиентское состояние — в
`static/app-v2.js`, визуализация — в `static/plan-25d.js`.

### elv-auditor

Текущий владелец:

- приёма DWG/DXF для аудита;
- преобразования DWG через ODA File Converter;
- разбора CAD-геометрии;
- консолидации стен;
- расчётных проверок инженерных систем;
- формирования отчётов и Excel;
- транспортного формата `geometry.v2`.

Основные файлы: `app/main.py`, `app/geometry_export.py`, `app/geometry_parser.py`,
`app/engine.py`, `app/schemas.py` и `app/services/wall_consolidator.py`.

## 2. Физическое хранение room-plan-editor

Проекты хранятся локально:

```text
data/projects/<project_id>/
├── project.json
└── <загруженные исходные файлы под уникальными именами>
```

Запись `project.json` выполняется через временный файл с последующей заменой.
Это защищает один файл от частичной записи, но не создаёт версий, транзакций
между несколькими объектами или резервных копий.

Старые глобальные файлы `data/project.json` и `data/geometry.json` используются
старыми endpoint'ами и переносятся в проект `initial` для совместимости.

## 3. Текущий ProjectRecord

Фактическая запись имеет следующую форму:

```text
ProjectRecord
├── id: string
├── name: string
├── files: ProjectFile[]
├── project
│   ├── project
│   │   ├── object
│   │   ├── address
│   │   └── revision
│   ├── floorPlan
│   │   ├── width
│   │   ├── height
│   │   ├── rooms
│   │   └── name?
│   └── equipment: Equipment[]
├── geometry: GeometryV2
├── cadSource?
├── cadPreview?
├── cadPreviewMaster?
├── cadGeometryMaster?
├── cadEquipmentMaster?
├── cadAreas?
├── cadLayouts?
├── cadSelectedLayout?
├── cadAppliedLayout?
├── archivedAt?
└── updatedAt
```

У ProjectRecord нет верхнеуровневого `schema_version`. Наличие и состав
необязательных CAD-полей отличаются между ранее созданными проектами.

## 4. Исходные файлы

Текущий элемент `files[]` содержит:

```json
{
  "id": "<uuid с расширением>",
  "name": "исходное имя файла",
  "size": 12345,
  "url": "/api/projects/<project_id>/files/<file_id>"
}
```

Поддерживаются PDF, DWG, DXF, PNG и JPEG до 250 МБ. Файл сохраняется рядом с
`project.json`. Контрольная сумма, MIME-тип, дата добавления, происхождение и
версия источника не записываются.

Исходный файл после сохранения не редактируется парсером. Однако запись проекта
не описывает формальную неизменяемость файла и не проверяет его хэш.

## 5. GeometryV2 в room-plan-editor

```json
{
  "version": 2,
  "canvas": {
    "width": 2650,
    "height": 1850
  },
  "walls": [],
  "doors": [],
  "windows": []
}
```

### 5.1. Wall

После серверной нормализации сохраняются:

```text
id
type: wall | partition
x1, y1, x2, y2
thickness
```

Импортированная стена до сохранения также может иметь `layer`, `source`,
`confidence`, `reviewHint`, `pairedGap` или `pairedGapMm`. Валидатор стен эти
поля сейчас отбрасывает. Происхождение и причина проверки после сохранения могут
быть потеряны.

### 5.2. Door

Сохраняются:

```text
id
wallId
x, y
width
rotation
swing: left | right | unknown
openingSide
leafCount
readerCount
accessPointId?
accessPointCode?
confidence?
reviewHint?
```

Дверь обязана ссылаться на существующую стену через `wallId`. Самостоятельной
сущности `Opening` нет; автоматически найденный дверной проём кодируется дверью
со `swing = unknown`.

### 5.3. Window

Сохраняются:

```text
id
wallId
x, y
width
rotation
```

Окно также обязано ссылаться на существующую стену.

### 5.4. Rooms

Комнаты могут присутствовать в `project.floorPlan.rooms` и в экспортном формате
`elv-auditor`, но не входят в сохраняемую `geometry` нового редактора как
полноценный редактируемый архитектурный объект.

## 6. Оборудование

Оборудование хранится плоским массивом `project.equipment[]`, отдельно от
`geometry`.

Основные поля:

```text
id
system
type
code
x, y
rotation
mount
mountingHeight
hostDoorId?
hostWallId?
status
```

Для контроллера дополнительно используются:

```text
formFactor
controllerDoorCapacity
controllerReaderCapacity
servedDoorIds[]
```

Текущие значения `system` включают:

```text
skud_intercom
cctv
sks
architecture
```

Системы не являются отдельными сущностями. Оборудование разных систем хранится
в одном массиве и разделяется значением поля.

## 7. Текущие связи

Самостоятельного массива `relations` нет. Связи встроены в объекты:

- дверь → стена через `wallId`;
- оборудование → дверь через `hostDoorId`;
- оборудование → стена через `hostWallId`;
- контроллер → двери через `servedDoorIds`.

Редактор блокирует удаление стены или двери, пока к ней привязано оборудование.
При перемещении стены или двери часть связанного оборудования перемещается вместе
с ней.

Связи не имеют собственного идентификатора, происхождения, статуса подтверждения
и истории.

## 8. CAD-поля и листы

Текущая CAD-модель использует:

- `cadPreviewMaster` — общая нормализованная подложка;
- `cadGeometryMaster` — полная извлечённая геометрия;
- `cadEquipmentMaster` — исходно найденное оборудование;
- `cadAreas[]` — найденные области Model Space;
- `cadLayouts[]` — имена доступных областей или листов;
- `cadSelectedLayout` — выбранное имя;
- `cadAppliedLayout` — имя, перенесённое на холст;
- `cadPreview` — текущая подложка выбранной области.

Отдельных сущностей `Sheet` нет. Все области используют одно поле `geometry` и
один массив оборудования. Выбор области может заменить текущую геометрию и
оборудование.

Среди существующих проектов встречаются записи с `cadSelectedLayout`, но без
`cadAppliedLayout`, что подтверждает неоднородность исторических данных.

## 9. Импорт CAD

Текущий импорт в `main.py`:

1. сохраняет загруженный DWG/DXF в проекте;
2. читает документ;
3. извлекает оборудование и геометрию;
4. строит CAD-подложку и области;
5. записывает master-поля;
6. напрямую записывает распознанную геометрию в `record["geometry"]`;
7. напрямую записывает найденное оборудование в `record["project"]["equipment"]`;
8. сохраняет ProjectRecord.

Если ранее выбранная область найдена в новом результате, импорт повторно
формирует её геометрию и также записывает её в рабочие поля.

Это означает, что сохранённые ручные изменения не защищены от повторного импорта.

## 10. Staging

В `static/app-v2.js` существует клиентское поле `state.stagingGeometry`.

Импорт `geometry.v2` позволяет:

- показать оранжевую геометрию поверх рабочей;
- отклонить её;
- принять её.

Ограничения:

- staging существует только в памяти браузерной страницы;
- после перезапуска не восстанавливается;
- не имеет ID, источника, версии алгоритма и истории;
- оборудование staging отдельно не моделируется;
- принятие заменяет всю `state.geometry` копией staging;
- частичное принятие отсутствует;
- отклонение не сохраняется как доменное решение.

`stagingGeometry` не является текущим аналогом полноценного `RecognitionRun` или
набора `Proposal`.

## 11. История и черновики

Undo/redo хранит до 100 полных снимков геометрии и оборудования в памяти
страницы. История очищается при загрузке проекта и после согласованного в рамках
интерфейса сохранения частей.

При наличии несохранённых изменений используется предупреждение
`beforeunload`. Автоматического проектного `Draft`, восстановления после
перезапуска и разрешения конфликта между draft и WorkingModel нет.

`localStorage` используется для настройки сворачивания галереи листов, а не для
хранения модели.

Редактор оборудования одной двери использует временную копию оборудования до
нажатия «Применить к плану». Это локальный черновик диалога, а не проектный
`Draft`.

## 12. Сохранение

Геометрия и оборудование сохраняются отдельными запросами:

```text
PUT /api/projects/{project_id}/geometry
PUT /api/projects/{project_id}/equipment
```

Интерфейс поддерживает независимые признаки `dirty` и `equipmentDirty` и две
кнопки сохранения. Единой версии сборки, проверки конкурентного изменения и
атомарного сохранения согласованной модели нет.

`updatedAt` меняется при каждой записи ProjectRecord, но не является версией
модели.

## 13. Issues

`room-plan-editor` не хранит самостоятельные issues. Необходимость проверки
частично кодируется полями объектов, например `swing = unknown` и `reviewHint`,
и отображается интерфейсом.

В `elv-auditor/app/schemas.py` существует ответ аудита:

```text
Issue
├── subsystem
├── severity: CRITICAL | WARNING
├── element
└── msg
```

Эти issues являются результатом одного расчётного ответа. У них нет ID, статуса,
времени, ссылок на несколько сущностей и постоянного хранения в ProjectRecord.

## 14. Формат elv-auditor geometry.v2

`app/geometry_export.py` формирует:

```json
{
  "version": 2,
  "schema_version": "2.0",
  "canvas": {},
  "walls": [],
  "doors": [],
  "windows": [],
  "rooms": [],
  "devices": [],
  "cable_routes": [],
  "metadata": {}
}
```

Метаданные могут включать источник, систему координат, параметры консолидации,
режим определения помещений и флаг ручной проверки.

`schema_version = "2.0"` относится к транспортному формату геометрии, а не ко
всему проекту. `cable_routes` существует как пустая заготовка и не образует
реализованную модель трасс.

## 15. 2.5D

Объёмный режим читает текущую геометрию и оборудование и строит условное
представление. Он не является отдельной моделью, не сохраняет собственную
геометрию и не изменяет проект.

Высоты, толщина и масштаб частично условны. 2.5D является представлением
рабочих данных, а не BIM или самостоятельным источником истины.

## 16. Архивирование и удаление

В текущем незакоммиченном серверном коде присутствуют:

- `archivedAt` в ProjectRecord;
- endpoint изменения архивного состояния;
- необратимое удаление каталога проекта после проверки архива и точного имени.

Эта реализация не содержит отдельной корзины, срока восстановления и журнала
удаления. Она не соответствует утверждённой целевой последовательности
`active → archived → trash → окончательное удаление` и не считается завершённой
моделью хранения.

## 17. Версии и миграции

Текущее состояние:

- `geometry.version = 2` версионирует только геометрию редактора;
- `geometry.v2.schema_version = "2.0"` версионирует экспорт аудитора;
- ProjectRecord не имеет `schema_version`;
- автоматические миграции отсутствуют;
- адаптеры чтения старых версий отсутствуют;
- неизменяемые Revision и Release отсутствуют.

## 18. Сущности, которых сейчас нет

В текущем постоянном хранилище отсутствуют самостоятельные:

- `Sheet`;
- `WorkingModel` как именованный согласованный блок;
- `Draft`;
- `RecognitionRun`;
- `Proposal`;
- `Revision`;
- `ValidationResult`;
- `Release`;
- `Relation`;
- постоянный `Issue`;
- `Origin`;
- `Verification`;
- `Placement`;
- `Route`;
- `RouteSegment`;
- `Cable`;
- `Tray`;
- `ConnectionPoint`;
- `Passage`;
- `Manifest`.

## 19. Основные текущие риски

1. Повторный CAD-импорт может перезаписать сохранённую ручную геометрию.
2. Выбор другой CAD-области может заменить геометрию и оборудование.
3. Принятие staging заменяет всю геометрию.
4. Staging и undo/redo теряются после перезапуска.
5. Происхождение стен теряется при серверной нормализации.
6. Геометрия и оборудование могут быть сохранены в несогласованных состояниях.
7. Исторические ProjectRecord имеют неодинаковый набор полей.
8. Отсутствие версии проекта не позволяет безопасно выполнять миграции.
9. Issues и связи нельзя надёжно агрегировать для дашборда.
10. Текущая модель удаления не обеспечивает восстановление из корзины.

расширяться желаемыми сущностями без отдельной пометки о том, что они отсутствуют.
