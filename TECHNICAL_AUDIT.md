# Технический аудит перед переходом к модели 0.1

Статус: карта текущего кода, рисков и требуемых изменений на 2026-09-17.

Целевые правила определены в `PRODUCT_ARCHITECTURE.md` и `DATA_CONTRACT.md`.
Фактическое хранение описано в `CURRENT_DATA_MODEL.md`.

## 1. Область аудита

Проверены два компонента:

- `room-plan-editor` — проектное хранилище, редактор и 2.5D;
- `elv-auditor` — импорт, распознавание, аудит и экспорт geometry.v2.

Аудит не подтверждает готовность целевой архитектуры. Его задача — определить,
какой текущий код нарушает или ещё не обеспечивает инварианты версии 0.1.

## 2. Краткий вывод

Рабочий фундамент существует:

- локальные проекты и исходные файлы;
- DWG/DXF-пайплайн;
- стены, перегородки, двери и окна;
- базовое оборудование СКУД, СОТ и СКС;
- встроенные связи с дверями и стенами;
- staging geometry.v2 в памяти;
- undo/redo в открытой странице;
- 2D и 2.5D;
- автоматические тесты основных взаимодействий.

Главный разрыв — распознавание, рабочая модель и выбранный лист используют одни и
те же поля ProjectRecord. Поэтому новый импорт может заменить подтверждённые
ручные данные.

## 3. Карта критических рисков

| Приоритет | Риск | Место | Текущее поведение | Требуемое поведение |
|---|---|---|---|---|
| P0 | Импорт заменяет рабочую геометрию | `room-plan-editor/main.py::parse_cad` | Результат записывается в `record["geometry"]` | Создать SourceFile, RecognitionRun и Proposal; WorkingModel не менять |
| P0 | Импорт заменяет оборудование | `main.py::parse_cad` | Найденное оборудование записывается в `project.equipment` | Хранить как предложения |
| P0 | Выбор листа заменяет модель | `main.py::select_cad_layout` | Geometry и equipment выбранной области становятся текущими | Выбрать пространственный контекст; создать/открыть Sheet; предложения хранить отдельно |
| P0 | Принятие staging заменяет всё | `static/app-v2.js::commitStagingGeometry` | `state.geometry` заменяется полной копией staging | Принимать выбранные Proposal атомарными операциями |
| P0 | Staging теряется | `static/app-v2.js::state.stagingGeometry` | Существует только в памяти вкладки | Сохранять RecognitionRun и Proposal в проекте |
| P1 | Теряется provenance стен | `main.py::validate_geometry` | `layer`, `source`, confidence и review hints отбрасываются | Сохранять Origin и Verification |

| P1 | Нет независимых листов | CAD-поля ProjectRecord | Один массив geometry для всех областей | Ввести Sheet внутри единой WorkingModel |
| P1 | Нет постоянных issues | auditor response и UI hints | Проблемы вычисляются или кодируются полями | Ввести Issue как сущность |

| P2 | Нет модели трасс | geometry export и editor | `cable_routes` пуст, доменных сущностей нет | Route, Cable, Tray и Relations |
| P2 | Нет Revision/Release | оба репозитория | Сохраняется только изменяемый проект | Неизменяемые снимки и manifest |

## 4. room-plan-editor: сервер

### 4.1. ProjectRecord

`create_project` создаёт старую структуру без `schema_version`, Sheets и
WorkingModel. Перед изменением формата необходим адаптер чтения legacy-записи,
иначе существующие проекты перестанут открываться.

### 4.2. Запись проекта

`write_record` безопасно заменяет один JSON-файл через временный файл. Это можно
сохранить как низкоуровневый механизм, но над ним нужны:

- проверка ожидаемой `model_version`;
- резервная копия перед миграцией;
- доменные операции;
- неизменяемое хранилище Revision и Release;
- запрет прямой записи вложенных полей из endpoint'ов.

### 4.3. Валидация геометрии

`validate_geometry` проверяет ID, координаты и ссылки дверей/окон на стены. Это
полезная основа, но функция одновременно нормализует и обрезает неизвестные поля.

Требуется разделить:

1. проверку транспортного payload;
2. миграцию старого объекта;
3. доменную валидацию;
4. сериализацию без потери Origin и Verification.

### 4.4. Валидация оборудования

`validate_equipment` проверяет типы, координаты и ссылки, а также ёмкость
контроллеров. Правила пригодны для будущего ruleset, но сейчас смешаны с записью
объекта.

Следует вынести:

- схему сущности оборудования;
- правила связности;
- правила готовности СКУД;
- формирование Issue;
- преобразование legacy-ссылок в Relation.

### 4.5. parse_cad

Функция выполняет слишком много обязанностей:

- принимает и сохраняет файл;
- читает CAD;
- распознаёт геометрию и оборудование;
- нормализует координаты;
- определяет области;
- выбирает активную область;
- записывает рабочую геометрию;
- записывает оборудование;
- сохраняет проект.

Это главный P0-узел. Его нужно разделить на:

```text
add_source_file
run_cad_recognition
persist_recognition_run
persist_proposals
```

Ни одна из этих операций не должна менять WorkingModel.

### 4.6. select_cad_layout

Функция сейчас является не выбором представления, а заменой данных. В целевой
модели она должна:

- выбрать или создать Sheet;
- изменить только навигационный контекст пользователя;
- показать связанную подложку;
- при необходимости создать RecognitionRun для выбранной области;
- не трогать другие листы и ручные данные.

### 4.7. Сохранение частей

`save_project_geometry` и `save_project_equipment` допускают промежуточно
несогласованное состояние. Переходный API может оставаться совместимым, но должен
внутри вызывать одну операцию обновления WorkingModel с optimistic locking.

### 4.8. Архив и удаление

Незакоммиченная реализация использует `archivedAt` и `shutil.rmtree`. До введения
корзины необратимое удаление не должно считаться готовой функцией. Требуется
отдельный StorageState и явная операция permanent delete только из trash.

## 5. room-plan-editor: клиент

### 5.1. Единый state без доменной границы

`state.geometry`, `state.equipment`, `state.stagingGeometry`, `savedGeometry` и
`savedEquipment` управляются независимо. Нет ID модели, model_version или
проверки конкурентного изменения.

Клиенту требуется единый `workingModel` и отдельный production state:

```text
draft
recognitionRuns
proposals
selectedSheetId
savedModelVersion
```

### 5.2. applyStagingGeometry

Функция полезна как визуальный адаптер geometry.v2, но она создаёт временный
объект без серверной идентичности. Её следует превратить в отображение уже
сохранённых Proposal.

### 5.3. commitStagingGeometry

Полная замена `state.geometry` нарушает инвариант приоритета ручных изменений.
Функцию нельзя использовать как основу нового принятия. Нужны операции выбора
Proposal, проверка target hash и ответ сервера с новой model_version.

### 5.4. Undo/redo

Текущий снимок geometry+equipment пригоден для локальных действий. После перехода
к WorkingModel история должна охватывать Relation и Issue либо хранить доменные
команды. Она не заменяет Draft и не обязана переживать выпуск.

### 5.5. Dirty state

Два dirty-флага отражают раздельное хранение. В целевой модели интерфейс должен
показывать единое состояние проекта:

```text
saved
unsaved
autosaving_draft
draft_saved
save_failed
conflict
```

### 5.6. beforeunload

Предупреждение остаётся дополнительной защитой, но не является механизмом
восстановления. После появления Draft закрытие страницы не должно приводить к
потере последнего автосохранённого состояния.

## 6. elv-auditor

### 6.1. geometry_export

`build_geometry_export` формирует полезный транспортный формат с метаданными,
source, confidence и manual review hints. Этот формат следует сохранить как
адаптер результата распознавания.

Необходимо изменить точку интеграции: geometry.v2 должен создавать Proposal, а
не заменять рабочую geometry.

### 6.2. adapt_room_plan_geometry

Адаптер принимает геометрию редактора и повторно консолидирует стены по группам
type/thickness. В будущем он должен принимать снимок Revision или явно
версионированный architecture block, чтобы проверка была воспроизводимой.

### 6.3. Issue в schemas.py

Текущий Pydantic Issue пригоден для ответа расчётного API, но недостаточен для
проектного Issue. Нужен адаптер из результата аудитора в доменную сущность с ID,
scope, status, refs, ruleset_version и датами.

### 6.4. Правила и версии алгоритмов

Экспорт уже содержит часть диагностических метаданных. Нужно формально добавить:

- имя алгоритма;
- версию алгоритма;
- версию ruleset;
- ID запуска;
- хэш исходного файла;
- хэш базовой рабочей модели.

Без этих данных RecognitionRun нельзя воспроизвести или корректно сравнить.

## 7. Дублирование между репозиториями

| Область | room-plan-editor | elv-auditor | Решение |
|---|---|---|---|
| Чтение DWG/DXF | `read_dwg`, `read_text_dxf` | `cad_converter`, API CAD | Выбрать общий адаптер или пакет |
| Извлечение стен | `extract_cad_geometry` | `geometry_export`, `geometry_parser` | Канонический recognizer в auditor |
| Консолидация стен | локальная collapse face pairs | `wall_consolidator` | Одна библиотека с версиями алгоритма |
| Классификация слоёв | строки и эвристики в `main.py` | aliases/parser | Версионированная конфигурация recognizer |
| Оборудование | `extract_equipment` | parser/engine | Auditor предлагает, editor хранит подтверждённое |
| Нормализация координат | `normalize_cad_*` | geometry metadata/origin | Единый coordinate transform в контракте |
| Issues | UI hints | AuditResponse | Auditor генерирует, project storage сохраняет |
| Сохранение проекта | локальный ProjectRecord | отсутствует | Канонический владелец — room-plan-editor |

На первом этапе необязательно физически переносить весь код. Достаточно запретить
двойное владение результатом и определить один контракт RecognitionRun/Proposal.

## 8. Проверки и тесты

На момент аудита в room-plan-editor проходят:

- 13 серверных тестов `tests/test_projects.py`;
- четыре Node test suite для centerline pairs, монтажа двери, взаимодействий
  редактора и 2.5D.

Эти тесты подтверждают текущую функциональность, но не покрывают целевой
жизненный цикл.

В окружении `elv-auditor` отсутствует исполняемый `pytest`, поэтому его suite не
был запущен в рамках этого аудита. Это не считается подтверждённым падением
тестов, но является пробелом воспроизводимости окружения.

## 9. Обязательные новые тесты

### 9.1. Защита WorkingModel

1. Сохранить ручную стену и дверь.
2. Запустить новый импорт.
3. Сравнить model_version и content hash WorkingModel до и после.
4. Убедиться в полном равенстве.

### 9.2. Сохранность RecognitionRun

1. Выполнить импорт.
2. Перезапустить сервер и клиент.
3. Получить тот же run и pending proposals.

### 9.3. Частичное принятие

1. Принять одно Proposal.
2. Проверить изменение только целевой сущности.
3. Проверить новую model_version.

### 9.4. Конфликт ручного изменения

1. Создать update Proposal с target hash.
2. Изменить объект вручную.
3. Попытаться принять Proposal.
4. Получить `conflict`, не изменив объект.

### 9.5. Независимые листы

1. Создать два Sheet.
2. Изменить первый.
3. Переключить второй и вернуться.
4. Проверить сохранность обоих наборов данных.

### 9.6. Draft

1. Изменить объект без явного сохранения.
2. Дождаться автосохранения Draft.
3. Перезапустить приложение.
4. Восстановить идентичное состояние.

### 9.7. Revision и Release

Проверить неизменяемость снимка, совпадение хэшей и запрет выпуска за пределами
validation scope.

## 10. Последовательность рефакторинга

### Фаза A — защита данных

1. Добавить schema_version через адаптер legacy-чтения.
2. Ввести SourceFile, RecognitionRun и Proposal storage.
3. Запретить прямую запись импортом в geometry/equipment.
4. Сохранить origin при нормализации.
5. Добавить тест неизменности WorkingModel.

### Фаза B — единая рабочая модель

1. Создать WorkingModel и model_version.
2. Преобразовать CAD-области в Sheet.
3. Перенести architecture и systems.
4. Выделить Relation и Issue.
5. Сделать атомарное сохранение.

### Фаза C — надёжность производства

1. Реализовать Draft и восстановление.
2. Реализовать Revision.
3. Версионировать ruleset и ValidationResult.
4. Реализовать Release и manifest.
5. Добавить viewer выпущенного комплекта.

### Фаза D — интерфейс производства

После прохождения вертикального сценария:

- производственный дашборд;
- очередь проверок;
- экран подготовки выпуска;
- паспорт и экспорт.

## 11. Условия начала дашборда

Дашборд можно начинать после выполнения всех условий:

- импорт не изменяет WorkingModel;
- RecognitionRun и Proposal переживают перезапуск;
- отдельное предложение принимается без полной замены модели;
- конфликт защищает ручное изменение;
- два листа сохраняются независимо внутри одной WorkingModel;
- Draft восстанавливается;
- проект имеет schema_version и миграцию;
- состояние готовности приходит из ValidationResult.

До этого дашборд может существовать только как дизайн-прототип без подключения к
нестабильной бизнес-логике.
